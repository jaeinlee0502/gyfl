# 계정·개인 서재·관리자 기능 연결

로그인 입구와 웹 화면은 GitHub Pages에서 제공합니다. 로그인 후 관리자가 교직원 이용을 승인한 계정과 관리자만 문제를 볼 수 있습니다. 문제 메타데이터와 이미지는 Supabase의 RLS 및 비공개 Storage에서 접근을 제한합니다. 관리자는 가입 신청 승인·승인 취소, 계정 검색, 임시 비밀번호 발급, 확인 후 일반 계정 삭제를 지원합니다.

**이메일 인증·복구 메일·SMTP는 사용하지 않습니다.** 이메일 형식의 문자열은 로그인 아이디로 사용하며, 가입자가 그 메일함을 소유하는지 확인한 값은 아닙니다. 비밀번호를 잊으면 사이트 관리자에게 문의합니다.

프로젝트는 `hwysnkiyqeeafqkjtrvn`, 사이트는 `https://jaeinlee0502.github.io/gyfl/`입니다. 마이그레이션 `202610250001`, `202610250002`를 적용하고 `account-admin` 서버를 배포했습니다. 실제 서버에서 메일 없는 가입·로그인, 사용자별 저장 목록 격리, 관리자 초기화·개인 비밀번호 변경·확인 후 삭제를 검증했으며 검증용 계정과 데이터는 정리했습니다. 운영자 본인 계정은 관리자 등록을 유지하며 새 프로젝트에서의 첫 관리자 지정은 아래 4번 절차를 따릅니다.

쓰기 권한이 있는 관리 토큰으로 DB와 서버 설치를 완료했습니다. `config/public-project.json`의 `ready: true`로 로그인 기능을 활성화합니다. 다른 새 프로젝트를 설정할 때는 설치와 검증 전까지 `ready: false`를 유지합니다.

새 프로젝트 설치 또는 서버 변경을 자동으로 진행하려면 해당 프로젝트에 한정한 관리 토큰에 다음 권한이 필요합니다. 토큰 교체 시에는 `SUPABASE_ACCESS_TOKEN` 비밀값을 갱신하고 클라우드 환경 설정을 저장·게시합니다. 토큰 값은 채팅이나 소스에 기록하지 않습니다.

| 권한 항목 | 필요한 범위 |
| --- | --- |
| Database | Read-write |
| Auth Config | Read-write |
| Project Settings | Read-write |
| Edge Functions | Read-write |
| API Keys | Read |

프로젝트 자체의 저장 용량 보호용 읽기 전용 모드는 꺼져 있습니다. 이 보호를 우회하거나 SQL로 거래 읽기 전용 설정을 해제하지 않으며, 관리 토큰의 정식 권한을 수정해야 합니다.

## 1. Supabase 인증과 공개 연결 설정

Supabase의 Authentication 설정에서 다음을 적용합니다.

- Email provider를 활성화하고 회원가입을 허용합니다.
- **Confirm email을 끕니다.** Management API 설정에서는 `mailer_autoconfirm: true`, `external_email_enabled: true`, `disable_signup: false`에 해당합니다.
- 비밀번호 최소 길이를 10자로 설정합니다.
- Site URL은 `https://jaeinlee0502.github.io/gyfl/`로 지정합니다. Redirect URLs에도 이 주소를 정확히 등록합니다. 이 서비스의 가입·초기화 과정에서는 메일 링크를 보내지 않습니다.

`config/public-project.json`에는 프로젝트 URL과 브라우저용 publishable key만 포함합니다. 이 두 값은 웹페이지에서 공개되는 연결 정보이며, 계정 데이터 접근 권한은 사용자 인증과 DB의 RLS가 판단합니다. `service_role`·secret key·DB 비밀번호·관리용 액세스 토큰은 이 파일이나 `VITE_` 변수에 넣지 않습니다.

다른 프로젝트로 연결하려면 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`를 함께 지정합니다. 로컬에서는 Git에서 무시되는 `.env.local`을 사용할 수 있습니다. GitHub Actions에서는 저장소의 **Settings → Secrets and variables → Actions → Variables**에서 공개 변수 두 개를 지정한 뒤 배포 워크플로를 실행합니다. 클라우드 환경 변수와 GitHub Actions 변수는 자동으로 서로 동기화되지 않습니다.

테스트는 운영 계정 서비스에 연결하지 않도록 독립된 모의 설정을 사용합니다. 브라우저 배포에는 publishable key 또는 legacy anon key만 허용하며, 잘못된 서버 키가 설정되면 빌드를 거절합니다.

## 2. 데이터베이스 설치

프로젝트 소유자 권한으로 Supabase CLI를 연결하고 마이그레이션을 적용합니다. 인증 정보는 CLI의 안전한 인증 흐름이나 클라우드 환경의 비밀값 설정에서 제공하며 채팅·소스에 기록하지 않습니다.

```bash
supabase login
supabase link --project-ref hwysnkiyqeeafqkjtrvn
supabase db push
```

CLI 대신 SQL Editor를 사용한다면 `supabase/migrations/202610250001_accounts_and_bookmarks.sql`, `202610250002_school_library.sql`을 순서대로 한 번씩 실행합니다. 초기 마이그레이션은 새 프로젝트를 기준으로 하므로 이미 같은 테이블이 있다면 스키마와 적용 이력을 먼저 확인합니다. 기존 데이터나 테이블을 삭제하여 재설치하지 않습니다.

- `profiles`: 사용자 ID, 이메일 아이디, 표시 이름. 본인 행 조회와 표시 이름 수정만 허용합니다.
- `bookmarks`: `(user_id, question_id)` 복합 키. 학교 이용 승인을 받은 본인 계정의 저장 목록만 조회·저장·삭제할 수 있습니다.
- `school_members`: 관리자에게 승인받은 교직원 계정입니다. 클라이언트는 본인 등록 여부만 읽고 직접 수정할 수 없습니다.
- `school_membership_audit`: 관리자 승인·승인 취소 기록입니다.
- `exam_questions`: 승인된 계정과 관리자만 읽는 문항 정보입니다.
- `school-questions`: 승인된 계정과 관리자만 인증 다운로드하는 비공개 Storage 버킷입니다. 일반 클라이언트 업로드는 허용하지 않습니다.
- `account_admins`: 신뢰할 수 있는 프로젝트 소유자 SQL 세션에서만 관리자 자격을 부여합니다. 일반 클라이언트는 본인 등록 여부만 읽습니다.
- `account_admin_audit`: 서버 전용 계정 지원 작업 기록입니다. 작업 종류, 대상, 수행자, 처리 상태와 시간을 남기며 비밀번호를 기록하지 않습니다.

모든 테이블에 RLS를 적용합니다. 비로그인 사용자는 계정 데이터에 접근할 수 없습니다. 가입자가 보낸 `user_metadata.role`이나 화면의 관리자 표시 여부는 서버 권한으로 사용하지 않습니다.

## 3. 관리자 서버 배포

```bash
supabase functions deploy account-admin
```

`SUPABASE_URL`과 `SUPABASE_SERVICE_ROLE_KEY`는 Supabase Edge runtime의 서버 전용 값입니다. 이를 프론트엔드로 복사하지 않습니다. 클라우드에서 프로젝트 설치·배포에 쓰는 `SUPABASE_ACCESS_TOKEN`도 브라우저 코드와 분리합니다.

허용할 브라우저 origin을 추가해야 한다면 Edge Function 설정의 `APP_ALLOWED_ORIGINS`에 쉼표로 구분한 정확한 origin을 지정합니다.

```text
APP_ALLOWED_ORIGINS=https://jaeinlee0502.github.io
```

origin에는 `/gyfl/` 같은 경로나 와일드카드를 넣지 않습니다. 로컬 호출이 필요하면 해당 `http://localhost:<port>` origin만 별도로 추가합니다.

`supabase/config.toml`의 `verify_jwt = false`는 최신 publishable key와 호환되는 gateway 설정입니다. 함수는 모든 실제 작업 전에 `auth.getUser(token)`으로 토큰을 검증하고 `account_admins`를 조회합니다. CORS나 클라이언트 표시만으로 관리자를 판단하지 않습니다.

## 4. 첫 관리자 지정

1. 운영자가 사이트에서 직접 사용할 계정을 만듭니다.
2. 프로젝트 소유자가 Authentication Users 또는 SQL Editor에서 **본인이 만든 정확한 사용자 UUID**를 확인합니다. 이메일 인증이 없으므로 이메일 문자열만 일치한다고 운영자 계정으로 판단하지 않습니다.

```sql
select id, email, created_at
from auth.users
where lower(email) = lower('본인-로그인아이디@example.com');
```

3. 확인한 본인 계정 UUID로 관리자 자격을 부여합니다. 아래 예시 UUID는 실제 확인한 값으로 바꿉니다.

```sql
insert into public.account_admins (user_id)
values ('확인한-본인-사용자-UUID')
on conflict (user_id) do nothing;
```

4. 로그아웃 후 다시 로그인해 관리자 메뉴를 확인합니다. 관리자 회수도 신뢰할 수 있는 소유자 SQL 세션에서 해당 UUID를 지정해 처리합니다.

```sql
delete from public.account_admins
where user_id = '확인한-사용자-UUID';
```

가입 화면이나 사용자 프로필 편집으로 관리자 권한을 받을 수는 없습니다. 관리자 비밀번호를 코드에 하드코딩하지 않습니다.

## 5. 관리자 계정 지원

관리자 화면을 열면 가입 신청·이용 승인 상태를 볼 수 있습니다. 학교 교직원 여부를 직접 확인한 뒤 이용 승인합니다. 승인 취소는 계정과 저장 목록을 유지하고 서재 접근을 제한합니다. 관리자 계정의 이용 권한은 이 화면에서 취소하지 않습니다.

관리자는 이름 또는 이메일 아이디로 일반 사용자 계정을 찾습니다. 한 번에 최대 20개 결과를 표시하므로 동명이인이면 검색어를 좁히고, 요청자 본인인지 확인한 뒤 작업합니다.

**비밀번호 초기화:** 서버가 강한 임시 비밀번호를 생성해 해당 계정의 비밀번호를 바꿉니다. 임시 비밀번호는 성공 응답에서 관리자에게 한 번 표시하며 로그·감사 기록·브라우저 저장소에 남기지 않습니다. 관리자는 이를 요청자에게 별도로 전달합니다. 선생님은 임시 비밀번호로 로그인한 뒤 계정 화면에서 본인의 새 비밀번호로 변경할 수 있습니다. 현재 구현은 첫 로그인 시 변경을 강제한다고 보증하지 않습니다. 기존 비밀번호 원문은 누구도 조회하지 않습니다.

**계정 삭제:** 관리자가 대상의 이메일 아이디를 다시 입력해 확인한 후 계정과 그 계정의 저장 목록을 삭제합니다. 삭제는 되돌릴 수 없습니다. 자기 계정이나 다른 관리자 계정은 이 지원 화면에서 초기화·삭제할 수 없습니다. 관리자 계정 자체의 복구나 권한 변경은 프로젝트 소유자가 별도 절차로 처리합니다.

초기화와 삭제에는 계정별 60초 대기, 관리자별 10분당 5건 제한을 적용합니다. 실패도 요청 기록과 제한에 포함됩니다. DB 예약을 잠금으로 직렬화하여 동시에 요청해도 제한이 우회되지 않도록 합니다. 감사 기록에는 계정 삭제 후에도 작업 수행자와 대상 UUID가 남을 수 있지만 비밀번호는 남지 않습니다.

## 6. 실제 연결 검증

개인정보가 없는 테스트 계정 두 개와 임시 관리자 계정으로 확인합니다. 테스트용 비밀번호·세션 토큰·서버 키를 출력하거나 저장하지 않습니다.

1. 비로그인 상태에서 로그인 입구만 표시되고 문항 메타데이터·원문 이미지 요청이 거부되는지 확인합니다.
2. 메일 없이 가입하면 승인 대기가 표시되는지, 관리자 승인 후 입장하며 승인 취소 후 문항·이미지 접근이 다시 거부되는지 확인합니다.
3. A 계정의 저장 문항이 다른 기기의 A 계정에서는 보이고 B 계정에서는 보이지 않는지 확인합니다. 다른 사용자 ID를 넣은 저장 요청도 거절되어야 합니다.
4. 일반 사용자 토큰의 관리자 API 호출과 메타데이터를 이용한 승격 시도가 거절되는지 확인합니다.
5. 관리자 초기화 후 임시 비밀번호로 로그인하고 새 비밀번호로 변경해 다시 로그인합니다. 감사 기록과 요청 제한도 확인합니다.
6. 잘못된 이메일 확인값·자기 계정·다른 관리자 계정의 삭제를 거절하고, 올바르게 확인한 테스트 사용자만 삭제되는지 확인합니다. 삭제 후 프로필·저장 목록도 제거되어야 합니다.
7. 계정 전환·로그아웃 시 이전 사용자의 저장 목록이 남지 않는지 확인합니다. 브라우저 저장 목록은 사용자가 가져오기를 선택할 때만 계정에 추가합니다.
8. 이번 검증에서 생성한 테스트 계정만 정리합니다. 실제 사용자의 계정이나 저장 목록은 테스트를 위해 삭제하지 않습니다.

자동 테스트와 로컬 모의 서버 검증, 실제 Supabase 연결 검증의 결과를 구분해 기록합니다. 실제 인증·데이터 분리·관리자 초기화와 삭제 검증이 끝나기 전에는 계정 서비스를 모두 준비됐다고 안내하지 않습니다.
